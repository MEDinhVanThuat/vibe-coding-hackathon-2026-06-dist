# 提出物の規定

> 言語: [English](submission.md) | **日本語** | [Tiếng Việt](submission.vi.md)

ハッカソン終了時刻 (1 時間 25 分経過時点) までに、以下の手順で提出してください。

## 提出フォーマット

**Pull Request を作成してください。**

PR の作り方:

1. このリポジトリを自分のアカウントに **fork** する（事前準備で済んでいるはず）
2. fork した自分のリポジトリで、`submit/<あなたの名前>` ブランチを作って作業する
   - 例: `submit/linh-nguyen`、`submit/hiroshi-tanaka`
3. 作業が終わったら（または締切が来たら）、自分の fork から **このリポジトリの `main` ブランチに対して PR を出す**

PR は merge されません（評価のためだけのスナップショットです）。動いてさえいれば「未完成」のままで OK です。

## PR 本文に書いてほしいこと

PR の説明欄に以下を含めてください。テンプレートとしてそのまま使ってもらって構いません。

```markdown
## 取り組んだタスク

- 着手した順に並べてください（user-stories.ja.md の番号で OK）
- 例:
  1. #1 UTC 日付ズレ → 完了
  2. #4 全文検索 → 完了
  3. #3 タグ機能 → 途中まで（API は完成、UI 未着手）
  4. #6 タイトル表示崩れ → 着手せず

## 優先順位の判断理由

なぜその順番で取り組んだのか、簡単に。
- どのストーリーが最も重要だと感じたか、その根拠は何だったか
- 後回し / 着手しなかったタスクを、なぜそうしたか

## AI ツールの使い方

- 使ったツール（Claude Code / GitHub Copilot / Cursor / その他）
- どこで AI に任せ、どこで自分で判断したか（具体的に 2-3 例）
- 任せて失敗した・期待通りに動かなかった例があれば
- 使ったツール固有の高度機能（サブエージェント / カスタムスキル / MCP サーバ / hooks / カスタムコマンド / プランモード等）を活用したなら、どう使ったか・何を得たか

## 動作確認

- 動かして確認した範囲（一覧表示、CRUD、新機能 ...）
- 残っている既知の問題（あれば）

## 自作した AI コンテキストファイル（任意）

当日中に AI コンテキスト用のファイルを自分で書いて repo に commit した場合、ここに書いてください。該当する例:

- ツール向け指示書（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `.github/copilot-instructions.md` / `.cursorrules`）
- ツール固有の設定ディレクトリ（`.claude/skills/` / `.cursor/rules/` / `.windsurf/` / `.continue/`）
- MCP サーバ設定（`mcp.json`）
- 使ったツールの同等物

含めなくても OK ですが、含めたなら何を書いたか（アーキ説明、規約、スキル定義など）を簡単に。AI の使い方の痕跡として価値があります。

## 追加で対応したこと（任意）

6 タスクを全部終えて時間が余ったので追加で改善した箇所があれば、ここに書いてください:
- 例: 「作成フォームに入力 validation を追加」「`app/web/lib/api.ts` のエラーハンドリングを整理」「ローディング表示を改善」
- 1 行ずつで OK
```

スクリーンショット添付は任意です。文字情報で十分伝わります。

## 締切

| 経過時間 | イベント |
|---|---|
| 0:50 | 重要度高タスクの仕様例を `upstream/main` に push（`git pull upstream main` で `tasks/specs/` を取得）|
| **1:25** | **提出締切（PR を Open 状態にする）** |
| 1:25-1:30 | 振り返り記入 (`docs/reflection-template.ja.md`) |

提出締切を過ぎても作業を続けるのは自由ですが、評価対象は **1:25 時点での PR 状態のスナップショット** です。

## 評価について

以下が評価の対象です:

1. **何を選び、何を後回しにしたか** — 数より理由を見ます
2. **AI ツールにどう振ったか・自分で判断したか** — 抽象論ではなく具体例で
3. **コードの品質・動作・回しすぎていないか** — 完璧でなく実用的に
4. 実装の完成度自体は副次的（全部終わっている必要はない）

competition ではなく、**個人診断**＋**組織レベルのツール効果レポート** のためのデータ収集が主目的です。完璧を目指して時間切れになるより、判断と振り返りが見える形で残してください。
